# B2 review · backend, ML and security plans

Reviewer: B2, the backend and ML lens of the v2 review swarm. Read at commit `12005bc`, Oct 24 from 2:20 to 2:55 PM PT.

Read: `docs/v2/contracts.md` (all of it, section 11 last), `docs/common/api-contract.md`, `docs/plans/B11-embed.md` to `B15-watch.md`, `I2-core.md`, `S3-catalog.md`, `server/main.py`, `server/config.py`, `server/routers/b08_approvals.py`, `tests/server/conftest.py` and `src/sources/live/b08-approvals.ts`. Also what those lean on: `src/sources/registry.ts`, `mode.ts`, `requests.ts`, `src/core/player.ts`, `tests/demo/beats.ts` and `harness.ts`, `scripts/server.mjs`, `scripts/secrets-scan.mjs`, `.claude/hooks/command-guard.mjs`, `docs/harness/lessons.md` and the offline pages in `docs/tech/` that landed during the review. `docs/v2/apis-and-accounts.md` didn't exist yet.

**Verdict: not ready.** Four blockers, each a small plan edit. With those fixed, the verdict is ready with fixes.

The plans get the hard parts of safety right. Keys pass through one config module. No agent can move money, publish or report, and a sweep test proves it. B15 never opens a found page and never sends anything. Every live path has a scripted twin. Request and response shapes follow the v1 rules, and each router's `evt_live_` range is its own. The ML plan refuses to round numbers in our favor. Tracing the data across step boundaries still turns up four blockers. An endless SSE stream hangs every uvicorn reload of the whole API, and the planned TestClient tests hang the same way. I reproduced both. Person-scoped IDs restart at 1 on each page load while SpacetimeDB keeps its rows, so B13 silently drops steps after the first reload. Nothing gets the trained model onto the Windows demo machines, and nothing checks that the model, `vectors.json` and the Elastic index match. The tour's live B14 runs can't land inside their beats, and G5's live-mode rule turns that into failed gates. On the ML side, the training run may not fit in 7 GB beside the dev servers, many hard negatives are right answers, and the proof compares a multilingual model with an English-only keyword baseline on queries an agent wrote, not a person.

**How I checked the claims that matter most:**
- uvicorn 0.54 source: `Server.shutdown()` waits while any connection is open, `timeout_graceful_shutdown` defaults to None, and the reloader's `restart()` calls `join()` on the worker.
- Starlette 1.7 TestClient on an endless `StreamingResponse`: still hung after 8 s, with the client done reading. The same stream ending after 1 s returned in 1.0 s.
- Python 3.13 `sum()` over 12 fair-random weights differed from a plain loop in 8,422 of 20,000 trials.
- The real command guard, run on a scratch project root against six commands that read keys.
- The `docs/tech/` pages for SpacetimeDB 2.13, Apify, Elastic Serverless and Agent Builder, sentence-transformers 6.2 and the e5 card. Where a finding rests on one, the evidence names it.

## The five fixes that matter most

1. Bound the B13 stream (about 20 s per response, `id:` lines with resume, a disconnect check each loop) and start uvicorn with `--timeout-graceful-shutdown 3`. Or replace SSE with short polling. (row 1)
2. Make person-scoped IDs unique per page load with a server-minted session tag, key SpacetimeDB rows by `seq`, and clear the swarm tables before a demo. (row 2)
3. Publish the trained model with its sha256, add a fetch step and a demo-machine setup step, and refuse to serve when the model, `vectors.json` and the Elastic documents don't share one fingerprint. (row 3)
4. Prefetch the tour's B14 runs at live-mode start with the tour's own IDs, use the cache only when it's ready, add the allowed-empty and required-key entries, and warm the model inside `health()`. (rows 4, 10, 11)
5. Train with frozen word embeddings, a 128-token cap, `NO_DUPLICATES` batches and filtered hard negatives, after a 3-step memory probe, in the background with one checkpoint per epoch under `models/`. (rows 5, 6)

The key guard and the secrets scan (rows 21 and 22) come next. Each takes minutes.

## Network calls

Offline-safe means the call never leaves this machine. No cloud call below runs in scripted mode. Adapters call `/api` only from `health()`, `produce()` and `start()`, and the registry runs those only in live mode (`registry.ts`, `mode.ts`). ## The three riskiest technical bets

1. **Our own model, trained on a 2 vCPU VM and carried to the demo machines (B11).** Everything downstream waits on it: B12's vectors, B14's Finder and Indexer, and B15's comparer. The chain of S3-catalog, B11's training run, B12 (3 h) and then B14 (5 h) is serial against about 15 hours left. The training run alone is close to an hour, and the planning session's container had no route to huggingface.co at all (`docs/tech/sentence-transformers/multilingual-e5-small.md`). **Fallback:** start B12, B14 and B15 against B11's `model.py` interface with the fake encoder as soon as B11 T6 lands, not after B11's G5. If the VM can't reach the hub, have the desktop download the base model once and upload it as a GitHub release asset, which the VM can fetch. If the fine-tune runs out of time or doesn't beat base, serve the base model as `cindia-embed-v0`, labeled "base model, not fine-tuned", with the honest report. Our vectors still go into Elastic. If no model reaches the demo machine, the tour plays search scripted with the real report numbers, badged Simulated.

2. **The live tour through the swarm under G5 (B14).** Four to six Claude calls in a row must land inside 6 to 10 second beats, three runs in a row, while G5 fails any healthy key that falls back. **Fallback:** prefetch the tour's runs at live-mode start and use the cache only when it's ready (row 4), so a beat plays scripted on time when it isn't. Prove B14 live with a person's question in a feature test, as B05 and B07 did. If latency still misses, keep the tour's B14 events scripted and say so on the end card, while people's questions in the drawers stay live.

3. **Shared live state on SpacetimeDB, streamed over SSE through a reloading dev server (B13).** It's the newest stack in the build: SpacetimeDB 2.13 with a TypeScript module, its HTTP API driven from Python, and an SQL dialect with no ORDER BY. It also carries the reload hang, the ID collisions on persistent rows and the open-port risk above. **Fallback:** short polling of `GET /api/b13/steps?after=<seq>` instead of SSE removes the reload hang, the TestClient hang and the connection pressure in one move. If the module won't publish, cut B13. B14's response already carries every step, and the swarm view still works.
